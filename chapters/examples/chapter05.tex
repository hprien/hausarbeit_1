\chapter{AI driven Penetration Testing}
\label{ch:chapter05}
Penetration Tests can either be performed by a software vendor it self or they can be delegated to a third party specialist. Costs that could be caused by data breaches and exploited vulnerabilities are significantly higher than costs of Penetration Tests. \cite{Gaafar_2024} However Penetration Tests are time consuming and labour intensive thus expensive dough. \cite{Confido_2022}

Tools like BurpSuite, ZAP and SQLMap already implement automated Penetration Testing techniques. They can be compared to \ac{DAST} scanning approaches. These automated scanners can support and enhance the process of Penetration Testing but these approaches do not show enough creativity to compete with human testers. \cite{Osman_2025}.

Earlier approaches to automate the process of Penetration Testing leveraged Reinforcement Learning. These \ac{AI} models were given a skill set e.g. networking tools like ping and nmap as well as concrete exploits. In training landscapes they were then trained to use these tools beneficially. \cite{Confido_2022} Scaling these Reinforcement Learning approaches to an production ready state brought up difficulties. One limiting factor is the need of high fidelity training environments. Also the maximum network size in which Penetration Tests can be performed by these tools is limited and not suitable for corporate networks. As the \ac{AI} needs to be provided and trained with individual exploits the set of these exploits is limited in size and adoption speed. \cite{Schwartz_2019}

Leveraging \ac{LLM}s for penetration testing shows better results and scalability in comparison to Reinforcement Learning. GPT-3.5 and GPT-4 without any technical additions are already capable of solving \ac{CTF} challenges. They are prompted to advice the user to execute a specific task like running a \ac{CLI} command which's output the user prompts back to the \ac{LLM}. This proves that \ac{LLM}s are already capable of performing Penetration Tests based on their built in domain knowledge. \cite{Deng_2024} The whole Penetration Testing process can be split up into multiple tasks. The architecture of PentestGPT introduced three agents to split these tasks. One agent responsible for information condensing, one for reasoning and one for concrete task planing. This agentic approach further improves the \ac{CTF} challenge completion rate. \cite{Deng_2024}

Now that \ac{LLM}s are capable of performing Penetration Tests in general a limiting factor is the seek of domain specific knowledge regarding specific known exploits. The project PentestAgent introduces this domain specific knowledge. It equips the agentic setup with a \ac{RAG}. Through this external knowledge base multiple vulnerability databases are introduces. Through several adjustments regarding the agentic setup and the additionally introduces domain specific knowledge the performance of \ac{LLM}s in Penetration Testing was improved even further. \cite{Shen_2025}

% Multiple tools already implement \ac{AI} for penetration testing to support human penetration testers \cite{Kozlovska_2025}.

The success of PentestGPT and PentestAgent are not limited to small networks or even single hosts. \ac{AI} Agents and thus \ac{LLM}s are also capable of performing Penetration Tests in real world and real size networks. ARTEMIS is a agentic approach like PentestGPT and PentestAgent. However it was optimized and tested in a real world university network. Just with the domain knowledge of GPT-5 it was able to compete with human penetration testers in terms of severity and complexity of findings. As mentioned by the architects of ARTEMIS this application tends to produce false positives. It scans systems in a broad mana instead of moving lateral like experience human penetration testers do. \cite{Lin_2025}

The vulnerabilities that PentestGPT, PentestAgent and ARTEMIS exploited in the benchmarks were nearly all performed based on known vulnerabilities or in controlled and thus not realistic test environments. For cooperate vendors especially web application Penetration Testing is highly interesting. This is because web applications are highly exposed and popular. Especially ARTEMIS and PentestAgent aims different fields than that. They concentrate more on network based attack and exploitation of known vulnerabilities. For finding new vulnerabilities in unknown web application environments these tools are not made and tested for.

Never the less these studies found that \ac{LLM}s are already capable of performing specific typed of Penetration Tests with their inherit domain knowledge. The usage of \ac{RAG} improves the Penetration Testing capability even further. These promising developments in using \ac{LLM}s for Penetration Testing are adopted by industrial software vendors like Google. Google published oss-fuzz, a \ac{LLM} powered fuzzing tool that actively found many security flaws in open source software. \cite{Happe_2025} An other example is XBOW which offers \ac{LLM} based Penetration Tests in real world cooperate environments. \cite{xbow2026}

Real world applications are much more complicated and unknown than test environments like DVWA, OWASP Juice Shop and OWASP WebGoat. They have dynamic pages with JavaScript logic and proprietary, sometimes niche technology stacks. Automated testing tools need to traverse the detailed architecture of the system under test. XBOW's high position on the Hackerone leaderboard proves that they are clearly capable of making valid findings in corporate infrastructure. \cite{hackerone_leaderboard} \cite{xbow_hype}

Corporate security experts who used XBOW on proprietary web applications shared their experiences for this term paper. According to the experts, XBOW is indeed capable of finding vulnerabilities, but they report that the tool tends to produce a high rate of false positives. The experts also note that valid findings made by XBOW are generally low-hanging fruits from the perspective of experienced penetration testers.

When it comes to proprietary technology stacks of web applications, the experts state that XBOW is not able to dig deep enough into the inner workings of proprietary frameworks. In their tests, the researchers used a deliberately vulnerable web application based on a proprietary technology stack as a benchmark system. The experts found that XBOW was unable to identify any vulnerabilities in this system.

The security expert who conducted these tests concludes that XBOW lacks the capability for lateral movement required to thoroughly investigate the working principles of the application.
